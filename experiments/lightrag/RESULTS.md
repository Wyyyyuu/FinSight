# LightRAG 首次实验结果：暂不替换原 RAG

日期：2026-09-14。结论仅适用于本地合成小样本：**主要收益来自真实向量，LightRAG图谱相对同向量基线未显示足够的净收益。建议继续保留现有RAG，LightRAG维持独立实验状态。**

原应用业务代码、默认路由、配置、根目录依赖和数据库未修改。密钥仍只保存在被Git忽略的本地实验配置。

## 实际执行范围

- 模型：DeepSeek官方API，`deepseek-flash`；完整实验统一显式非思考模式、temperature=0。
- 相同真实向量：`BAAI/bge-small-zh-v1.5`，512维，本地ONNX；独立hash诊断组为1024维。
- 16篇完全虚构的金融证据、12题；其中10题有标准证据，2题应承认证据不足。不能据此判断真实财报准确性。
- 4组×12题=48份生成回答；每题每组检索3次，共144次检索。Top-K=4，最大上下文3000 tokens；没有按题预先筛选正确文档，没有向检索器/生成模型提供标准答案。
- 10项实验单元检查通过，35项原有RAG回归通过。首次pytest有缓存目录权限警告，不影响通过结果；后续实验检查关闭了缓存插件。
- 首次API JSON请求成功，本地向量实际输出512维；LightRAG完整入库16/16，失败0；完整四组运行48/48，运行/评分解析错误0。这不等于质量验收通过。

| 原检索器 + hash | 25.83% | 10% | 0.2343 | 1.90 ms | 1.58 ms |
| 原检索器 + 真实向量 | 82.50% | 60% | 0.8680 | 7.21 ms | 6.35 ms |

mix相对主基线的Recall只增加**0.83个百分点**，原文齐备率不变，排序指标略降。48个“问题×检索器”组合的warm结果均稳定。检索的标准答案只标注必需原文，图节点和边不计为原文命中，因此这些值应称为“原文召回”，不是完整图谱知识召回。

差异主要来自两题：

- `supplier_chain`：mix的必要原文召回从1/3提高到2/3，补到了QM基板与封装商的关系，但仍缺少检修减产的原始公告。
- `cloud_chain`：mix从3/4降到2/4，反而遗漏了供应链中间环节的原文。

首次查询发生在索引已建好之后，不是进程/模型冷启动；mix包含一次关键词LLM调用。warm是同题重复查询并允许关键词缓存，不代表所有真实请求都能享受缓存。两类耗时分别列示，不使用缓存后的数字掩盖首次查询开销。小样本p95不适合推断生产容量。

## 建图与成本

- 原检索器真实向量入库16篇约0.164秒；LightRAG完整图索引约21.913秒，涉及17次LLM调用。两种LightRAG查询模式共用该索引，不能将这个成本当作naive专用向量索引成本。
- LightRAG索引文件约903,213字节，含图、向量、状态与缓存；不是生产数据库规模估计。
- 完整配对运行共125次LLM调用：建图17次、关键词检索12次、回答48次、Judge 48次。
- 完整配对运行已知输入101,978 tokens、输出17,940 tokens，合计119,918 tokens；服务均返回usage。
- mix的12份回答输入为28,380 tokens，主基线为3,378 tokens。双方上限相同，但图谱消耗了更多实际上下文，不能把潜在回答改善解释成“无额外成本的图推理”。
- 修复后的回放另有15次请求尝试，12次成功、3次连接失败后单独重试；成功用量共16,386 tokens。连接失败未返回usage，不能推定为零成本。
- 最初中止的思考模式建图运行未完整落盘请求用量，另有一次接口预检。本报告中的完整运行用量**不是账户本次全部账单总量**。未配置价格，未估算货币成本。

## 为什么不以模型自评分宣称答案质量提高

原始Judge把mix答案覆盖均分评为95.83%，主基线为79.17%。复核发现至少两处明确不可靠：

1. `negative_chain / legacy_hash`：回答因缺少采购链而无法判断，却被Judge判覆盖率1；该题的标准答案要求说明已知链条不支持依赖QM基板。
2. `supplier_chain / lightrag_mix`：回答明确缺少检修事件证据，遗漏减产20%与预计恢复时间，Judge仍判覆盖率1。

因此，`answer_coverage`、`faithfulness`和`citation_support`这些同模型自评分保留作诊断，**不用于证明质量收益，也没有对错误分数进行事后手工美化**。如要得出答案质量结论，需独立逐要点评判、真实语料和人工抽查。

## 发现并修复的来源问题

初始适配器只把LightRAG的text chunks作为提供的原文，但同时把图谱描述和来源字段放进上下文。图谱可能来自Top-K之外的文档，从而绕过原文提供范围。

原始mix在`cloud_chain`和`negative_chain`两题中，引用了没有实际提供原文的S01/S02/S04。这些来源存在于完整题集，并不等于凭空编造来源；问题是**适配器没有让图谱、原文和引用边界保持一致**，不能归因于LightRAG本身必然产生错误。

修复：只有图谱描述的全部原始来源已经进入实际上下文时，才允许该描述进入生成阶段；还检查描述中嵌入的来源编号。增加了对应离线回归检查。

针对保存的同一批召回结果，重新生成mix的12份回答：

- 初次9份成功、3份连接失败；仅重试这3份后，12/12完成。
- 12份回答均有引用，没有引用未提供原文的ID；**这只验证来源编号边界，不等于事实忠实度100%**。
- 两个出问题的供应链回答改为明确说明缺少中间环节原文，不能补全链条。
- 该回放没有重跑检索或Judge，不能当作第二轮完整四组质量/性能数据。上表保留第一次完整运行的原文召回和检索耗时。

## 采用建议

当前不切换生产默认实现。优先确保部署中的真实embedding实际生效，再用有原始出处的财报和电话会扩大题集。只有在来源约束下，多跳必要证据和独立评估的答案要点覆盖获得稳定提升，且建图与查询成本可接受，才考虑将LightRAG接入长期KB。现有memory/WS生命周期、TTL、权限与Inspector仍需要独立集成验收。
